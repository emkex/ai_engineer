1. Пользователь явно просит подготовить папку для изучения библиотеки:

## PURPOSE

Этот скилл решает проблему: каждый раз при изучении новой библиотеки нужно:
1. Прочитать документацию (несколько страниц)
2. Прочитать презентацию (десятки слайдов)
3. Разобрать практику (notebook / скрипты)
4. Создать файлы-примеры с пояснениями

Скилл автоматизирует весь этот цикл за один запрос.

Авторизует агента на:
- Чтение PDF файлов (презентации)
- Fetch URL документации (несколько страниц параллельно)
- Чтение .ipynb и .py файлов практики
- Создание папки `<N>_week/<lib_name>/` с файлами-примерами

Явно запрещает:
- Создавать файлы вне папки недели (`<N>_week/`)
- Использовать домен задач НЕ финансовый
- Раскрывать замысел fin_advisor в публичных файлах
- Хардкодить API-ключи

---

## CORE RULES (NON-NEGOTIABLE)

1. **Финансовый домен** — все задачи и примеры в финансовом домене: тикеры, сигналы, новости, портфели, ликвидность, потоки капитала. Без исключений.

2. **Русские комментарии** — все `#` комментарии и docstring на русском языке.

3. **Ссылки на слайды** — каждая секция кода содержит `# Слайд N: ...` со ссылкой на конкретный слайд презентации. Если PDF не предоставлен — ссылки на документацию.

4. **Параллельное чтение** — PDF и URL документации читаются параллельно (Agent subagent или параллельные Read/WebFetch вызовы).

5. **Минимум 4 файла** — создаётся не менее 4 .py файлов, последний всегда — разбор практики (notebook_walkthrough или practice_explained).

6. **Папка назначения** — `<N>_week/<lib_name>/` где N — текущая неделя обучения из CLAUDE.md или из контекста. Если неделя неясна — спросить.

7. **Без API ключей** — файлы содержат комментарий `# os.environ["KEY"] = ...` или dotenv, никогда не хардкодят ключи.

8. **Размер файлов** — каждый файл ≤ 500 строк. Если тема большая — разбить на несколько файлов.

9. **fin_advisor секрет** — финансовый домен используется для задач нейтрально (тикеры, OHLCV, сигналы). Никогда не упоминать fin_advisor или конкретные алгоритмы из него.

## DOCUMENT / RESOURCE SPECIFIC RULES

### PDF презентации
- Читать все страницы (по 20 за раз если PDF большой)
- Для каждого блока/темы запомнить номера слайдов
- Использовать слайды как ссылки в комментариях: `# Слайд 15: BaseModel — контракт, а не просто класс`

### URL документации
- Читать параллельно: обзор + core concepts + key API pages
- Извлекать: ключевые классы/функции с параметрами, code examples, что решает
- Если документация большая — приоритет: getting started, core concepts, API reference

### .ipynb / .py практика
- Разобрать каждую ячейку/блок: ЗАЧЕМ это написано, КАК работает, ЧТО не раскрыто
- Последний файл всегда: построчный разбор практики с пояснениями

## PROTOCOL (STRICT ORDER)

### Step 1 — Сбор источников
Определить из запроса пользователя:
- Имя библиотеки
- URL документации (если есть)
- Путь к PDF презентации (если есть)
- Путь к .ipynb/.py практике (если есть)
- Номер недели / папка назначения

Если папка назначения неясна → спросить. Если нет ни одного источника → спросить.

### Step 2 — Параллельное чтение
Запустить одновременно:
- Чтение PDF (если есть) — по 20 слайдов за раз
- Fetch документации — несколько ключевых страниц через Agent(subagent_type=Explore)
- Чтение .ipynb/.py (если есть)

### Step 3 — Синтез структуры файлов
На основе прочитанного определить:
- Ключевые концепции библиотеки (обычно 4-6)
- Порядок файлов (от базового к сложному)
- Какой файл будет разбором практики

Стандартная структура:
- `01_basics.py` — базовые концепции без AI/agent
- `02_core_feature.py` — главная фича библиотеки
- `03_advanced_feature.py` — продвинутые возможности
- `04_<last_topic>.py` — специфичная тема (зависит от библиотеки)
- `05_notebook_walkthrough.py` — разбор практики построчно

### Step 4 — Создание файлов
Создать папку и все файлы параллельно если возможно.

#### Структура каждого файла (ОБЯЗАТЕЛЬНО)

**Шапка файла:**
```python
"""
ФАЙЛ N: <Название> — <краткое описание>
======================================
Документация: <url>
Слайды: N–M
"""
```

**Каждая секция кода:**
```
# =============================================================================
# НАЗВАНИЕ СЕКЦИИ / ШАГ N
#
# ЧТО ЕСТЬ: что уже сделано к этому моменту (контекст)
# ПРОБЛЕМА (если есть): зачем нужен этот шаг, что без него не работает
# ЧТО ДЕЛАЕМ: конкретное действие в этой секции
# КАК РАБОТАЕТ: пошагово что происходит при выполнении кода
#   1. ...
#   2. ...
#
# Слайд N: <цитата или ключевая фраза>
# =============================================================================

<код>
```

**Правила секций:**
- Нумеровать шаги: `# ШАГ 1:`, `# ШАГ 2:` ... (для файлов с единым потоком)
- Или называть по концепции: `# УРОВЕНЬ 1:`, `# CIRCUIT BREAKER:` (для файлов с примерами)
- `ЧТО ЕСТЬ` — всегда присутствует: что пользователь уже знает/имеет
- `ЧТО ДЕЛАЕМ` — одно конкретное действие
- `КАК РАБОТАЕТ` — пронумерованные шаги выполнения, не абстрактное описание
- После каждого крупного блока (2-4 секции) — `# SUMMARY` с итогом блока на английском

**Обязательные технические требования:**
- `from dotenv import load_dotenv` + `load_dotenv()` в каждом файле с LLM-агентом
- Никогда не хардкодить API ключи
- Заглушки (mock data) вместо реальных HTTP-запросов в примерах
- `model="anthropic:claude-haiku-4-5-20251001"` как дефолтная модель (Anthropic API)
- Рабочий код (без реальных API вызовов или с заглушками)
- Финансовый домен в задачах

### Step 5 — Подтверждение
Вывести таблицу созданных файлов с кратким описанием.
Ответить на вопрос "что ещё не раскрыто" — что есть в документации но не вошло в файлы.

## BAD EXAMPLES

### Плохой пример 1 — домен не финансовый
Задачи про "классификацию тикетов поддержки", "рецепты еды", "города".
Почему неверно: нарушает правило финансового домена. Всегда: тикеры, портфели, сигналы.

### Плохой пример 2 — нет ссылок на слайды
Файлы созданы без `# Слайд N:` в комментариях.
Почему неверно: пользователь не сможет сопоставить код с теорией.

### Плохой пример 3 — нет разбора практики
Созданы 4 файла с примерами, но ноутбук не разобран.
Почему неверно: главная цель — понять конкретную практику, последний файл обязателен.

### Плохой пример 4 — хардкод ключа
```python
os.environ["OPENAI_API_KEY"] = "sk-abc123..."
```
Почему неверно: нарушает git-safety правила. Всегда через dotenv или комментарий.

1. Что делает парсер — общий поток данных

Парсер каждые N секунд заходит на benzinga.com/markets, собирает ссылки на статьи, читает каждую статью и делает две вещи одновременно:

очередь сообщений
←(другие потребители)

Зачем два хранилища?

MongoDB — долгосрочная история. Чтобы не парсить одну статью дважды (есть find_news) и хранить всё для анализа.

RabbitMQ — очередь для реального времени. Другой сервис (ML-модель, уведомления, торговый бот) подписывается и получает новости мгновенно, не опрашивая БД.

2. RabbitMQ — что это и зачем

Аналогия: почтовое отделение

Представь, что парсер — это курьер, который приносит письма (новости). MongoDB — это ящик, куда он сам кладёт копию каждого письма. А RabbitMQ — это почтовое отделение с сортировкой: курьер оставляет письмо там, и дальше оно само расходится по адресатам (другим программам).

Без RabbitMQ

  • Парсер должен сам знать про всех потребителей
  • Если потребитель упал — данные теряются
  • Парсер ждёт пока потребитель обработает

С RabbitMQ

  • Парсер кладёт в очередь и сразу идёт дальше
  • Потребитель поднялся — заберёт накопившееся
  • Можно добавить нового потребителя без правки парсера

Ключевые понятия RabbitMQ

ПонятиеЧто этоВ коде
ExchangeТочка входа сообщений. Решает, в какую очередь отправитьexchange='' — default exchange, напрямую в очередь
Queue (очередь)Список сообщений, ждущих обработкиqueue_name = 'news'
ProducerКто кладёт сообщенияRabbitSender.send()
ConsumerКто забирает и обрабатываетОтдельный сервис (в этом проекте не написан)

Реальный RabbitMQ — это реальный сервер

Да, это реальный брокер! Это отдельная программа (написана на Erlang), которая запускается как сервис — в этом проекте в отдельном Docker-контейнере. У него есть веб-интерфейс на порту 15672 (http://localhost:15672), где можно наглядно видеть очереди, сообщения, потребителей.

3. pika — Python-клиент для RabbitMQ

pika — это просто Python-библиотека, которая умеет разговаривать с RabbitMQ по протоколу AMQP. Это как requests для HTTP, только для RabbitMQ.

# rabbit_sender.py — разбираем строку за строкой

import pika  # Python-клиент для RabbitMQ

# 1. Описываем параметры подключения — адрес, логин, пароль
self.rabbitmq_params = pika.ConnectionParameters(
    host=host,       # "rabbitmq" — имя контейнера в docker-compose (это как hostname)
    port=port,       # 5672 — стандартный порт AMQP
    credentials=pika.PlainCredentials(username=username, password=password)
)

def send(self, message):
    # 2. Открываем соединение (TCP-соединение с RabbitMQ)
    connection = pika.BlockingConnection(self.rabbitmq_params)

    # 3. Канал — логический поток внутри соединения
    channel = connection.channel()

    # 4. Объявляем очередь (создаёт если нет, ничего не делает если есть)
    channel.queue_declare(queue=self.queue_name, durable=True)

    # 5. Публикуем сообщение
    channel.basic_publish(
        exchange='',                    # default exchange
        routing_key=self.queue_name,    # имя очереди-получателя
        body=message,                   # JSON строка с новостью
        properties=pika.BasicProperties(
            delivery_mode=2             # persistent — не теряется при рестарте
        )
    )
    connection.close()  # закрываем соединение после каждого сообщения
Недостаток Соединение открывается и закрывается для каждого сообщения. Это медленно — лучше было бы держать одно постоянное соединение. Но для учебного проекта — нормально.

4. MongoDB — что это и чем отличается от SQL

Ты знаешь pandas + CSV — объяснение через это

CSV / pandas (что ты знаешь)

  • Данные — строки и столбцы
  • Все строки одинаковой формы
  • Хранится в файле на диске
  • Нет встроенной защиты от двух одновременных записей
  • Нет индексов — поиск медленный

MongoDB (что здесь используется)

  • Данные — JSON-документы (dict в Python)
  • Каждый документ может иметь разную структуру
  • Хранится на сервере, поддерживает тысячи запросов в секунду
  • Конкурентная запись безопасна
  • Индексы — поиск быстрый

MongoDB vs SQL (PostgreSQL)

SQL (PostgreSQL)MongoDB
СтруктураТаблицы со строгой схемойКоллекции JSON-документов
СхемаНужно заранее создать таблицу с типамиСхемы нет — пишешь что хочешь
ЗапросыSQL языкPython-методы: find(), insert_one()
СвязиJOIN между таблицамиВсё в одном документе (обычно)
Когда лучшеСтруктурированные данные, транзакцииГибкие данные, быстрый старт
АналогияExcel-таблица с жёсткими столбцамиПапка с заметками, каждая своя

Как MongoDB устроена внутри

# Вот что сохраняется в MongoDB при парсинге одной новости:
{
    "_id": ObjectId("..."),              # auto-generated unique ID
    "reference": "https://www.benzinga.com/...",
    "title": "Bitcoin surges 10% on news...",
    "body": "The cryptocurrency market..."
}

MongoDB: Database → Collection → Document
Аналог SQL:       Database → Table        → Row

Почему MongoDB здесь? Новость — это JSON. В MongoDB она ложится напрямую без маппинга на таблицы. Поле reference легко индексировать для быстрой проверки «была ли эта новость уже»?

5. AsyncIOMotorClient — асинхронный драйвер

motor — это Python-библиотека. Название Motor = Mongo + asyncio + driver. Она нужна, чтобы работать с MongoDB через async/await.

pymongo (синхронный)

client = MongoClient(uri)
result = collection.find_one(...)
# программа ЖДЁТ здесь
Пока MongoDB отвечает — весь парсер стоит

motor (асинхронный)

client = AsyncIOMotorClient(uri)
result = await collection.find_one(...)
# программа ПРОДОЛЖАЕТ другие задачи
Пока MongoDB отвечает — парсер качает другие статьи 
# mongo_storage.py — разбираем строку за строкой

from motor.motor_asyncio import AsyncIOMotorClient

async def connect(self):
    # Создаём async клиент — не блокирует event loop
    client = AsyncIOMotorClient(self.mongo_uri)
    db = client.get_database(self.db_name)  # db = "parser_db"
    return db

async def save(self, news_entry):
    db = await self.connect()
    collection = db.get_collection(self.collection_name)  # коллекция "news"
    await collection.insert_one(news_entry)  # вставляем документ

async def find_news(self, reference):
    db = await self.connect()
    collection = db.get_collection(self.collection_name)
    # count_documents({поиск}) > 0 — проверяем: была ли уже такая ссылка?
    return await collection.count_documents({"reference": reference}) > 0
Недостаток connect() создаёт нового клиента при каждом вызове. Лучше создать клиент один раз в __init__ и переиспользовать. Но для учебного проекта — работает.

6. Dockerfile — образ и контейнер подробно

Главная аналогия: рецепт и блюдо

Dockerfile = кулинарный рецепт (инструкция что и как делать)
Image (образ) = приготовленное блюдо в вакуумной упаковке (можно хранить, копировать)
Container (контейнер) = блюдо, которое вынули из упаковки и едят (работающий процесс)

Что такое образ технически

Образ — это набор слоёв (layers). Каждая инструкция Dockerfile создаёт один слой. Слои кэшируются — если ничего не изменилось, Docker не пересобирает слой заново.

Полный разбор Dockerfile проекта

FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "src/app.py"]
FROM
FROM python:3.11-slim
Берём базовый образ. Docker скачивает готовый образ с Linux + Python 3.11. slim — урезанная версия без лишних инструментов (меньше весит, более безопасна).
Аналог: берёшь чистую ОС с уже установленным Python
WORKDIR
WORKDIR /app
Устанавливаем рабочую директорию внутри контейнера. Все последующие команды (COPY, RUN, CMD) выполняются относительно этого пути. Если папки нет — создаётся автоматически.

Почему /app, а не /usr/src/myapp? Чисто соглашение. /app — современный стандарт, коротко и понятно. /usr/src/myapp — тоже валидно, но устарело. Главное — быть последовательным.
Это директория ВНУТРИ контейнера, не на твоём компьютере
COPY
COPY requirements.txt .
Копирует файл(ы) с твоего компьютера (хоста) в образ.
Синтаксис: COPY <откуда_на_хосте> <куда_в_образе>
Точка . означает «в текущую директорию» = в /app (потому что WORKDIR /app).

Почему сначала только requirements.txt, а не всё сразу?
Кэширование слоёв! Docker кэширует каждый слой. Если ты изменил код (app.py), но не изменил requirements.txt — Docker не будет переустанавливать пакеты, возьмёт из кэша. Это экономит минуты при каждой пересборке.
RUN
RUN pip install --no-cache-dir -r requirements.txt
Выполняет команду при сборке образа (не при запуске).

--no-cache-dir — не сохранять кэш pip внутри образа. Пакеты уже установлены, кэш больше не нужен → образ меньше весит. Это НЕ про кэш Docker-слоёв — это про pip-кэш внутри контейнера.

Слой с пакетами создаётся один раз. Пока requirements.txt не меняется — Docker берёт этот слой из кэша при каждой пересборке.
COPY . .
COPY . .
Копирует всё остальное — весь код проекта (src/, Dockerfile, etc.) в /app.
Первая точка — корень проекта на хосте (там где Dockerfile).
Вторая точка — /app в образе.

Этот слой пересоздаётся каждый раз при изменении кода — это нормально и быстро.
CMD
CMD ["python", "src/app.py"]
Команда, которая запустится при старте контейнера.
Это не выполняется при сборке образа — только при docker run.
Формат JSON-массива предпочтителен (не CMD python src/app.py) — он не использует shell, процесс стартует напрямую.

Итог: контейнер запускается → Python запускает src/app.py → парсер работает

EXPOSE — почему его нет здесь?

EXPOSE 8080 — документационная инструкция. Она говорит "этот контейнер слушает порт 8080", но ничего не открывает сама по себе. Реально открывают порты флаги -p в docker run или секция ports в docker-compose.

Парсеру не нужно принимать входящие запросы — он сам ходит в интернет. Поэтому EXPOSE не нужен.

Образ vs контейнер — финальное понимание

ДействиеКомандаЧто происходит
Собрать образdocker build -t parser_app .Dockerfile выполняется строка за строкой, создаётся image
Запустить контейнерdocker run parser_appИз image создаётся рабочий контейнер, запускается CMD
docker-compose updocker-compose up -dСобирает образы (если надо) + запускает все контейнеры
Твоё понимание верное: Dockerfile = рецепт всего. Он объединяет: базовый образ + установку пакетов + копирование кода + команду запуска. Без него пришлось бы делать всё по шагам вручную через docker exec.

7. docker-compose.yml — оркестрация трёх контейнеров

docker-compose — инструмент для запуска нескольких контейнеров как одного приложения. Вместо трёх команд docker run — один файл и одна команда.

Полный разбор docker-compose.yml

version: '3'  # версия формата файла (не версия docker-compose)

services:   # список контейнеров которые будут созданы

  web_app:                 # имя сервиса (придуманное нами)
    build:
      context: .           # папка, которую передать Docker при сборке
      dockerfile: Dockerfile # какой Dockerfile использовать
    depends_on:
      - mongo               # запустить mongo ПЕРЕД web_app
      - rabbitmq            # запустить rabbitmq ПЕРЕД web_app
    networks:
      - parser_network      # подключить к внутренней сети
    env_file:
      - .env                # передать переменные окружения из .env

  mongo:                   # MongoDB сервис
    image: mongo:7.0.4-jammy # готовый образ с Docker Hub (не собираем сами)
    container_name: mongo-container
    ports:
      - "27017:27017"        # хост:контейнер — открываем для внешнего доступа
    environment:
      MONGO_INITDB_ROOT_USERNAME: user
      MONGO_INITDB_ROOT_PASSWORD: user
    volumes:
      - mongo_data:/data/db  # сохраняем данные за пределами контейнера
    networks:
      - parser_network

  rabbitmq:
    image: rabbitmq:management # готовый образ с веб-интерфейсом
    container_name: rabbitmq-container
    ports:
      - "5672:5672"          # AMQP порт — для подключения pika
      - "15672:15672"        # HTTP UI — http://localhost:15672
    environment:
      RABBITMQ_DEFAULT_USER: user
      RABBITMQ_DEFAULT_PASS: user
    networks:
      - parser_network

networks:
  parser_network:
    driver: bridge          # тип сети: изолированная внутренняя сеть

volumes:
  mongo_data:              # именованный том — Docker управляет сам

build vs image — в чём разница

build:

Говорит: "собери образ сам из Dockerfile"
Используется для твоего кода
context: . — отдай всю текущую папку

image:

Говорит: "скачай готовый образ с Docker Hub"
Используется для сторонних сервисов
image: mongo:7.0.4-jammy — официальный образ MongoDB

Оптимально ли 3 контейнера для парсера?

Да, это стандартная и правильная архитектура. Каждый контейнер — одна ответственность (Single Responsibility на уровне инфраструктуры):

  • Обновить версию MongoDB? Меняешь только mongo-контейнер
  • Парсер упал? MongoDB и RabbitMQ продолжают работать, данные не теряются
  • Хочешь добавить второй парсер? Запускаешь ещё один web_app контейнер
  • Масштабируешь MongoDB отдельно? Легко
Альтернатива — один монолитный контейнер со всем. Проще, но теряешь всё вышеперечисленное.

8. Порты, тома (volumes), сети (networks) — подробно

🔌 Порты

Каждый контейнер живёт в своей изоляции. По умолчанию снаружи к нему не достучаться. Порты — это "дыры" в этой изоляции.

ports:
  - "27017:27017"
#   ↑        ↑
#   |        └── порт ВНУТРИ контейнера (слушает MongoDB)
#   └─────────── порт на ТВОЁМ компьютере (хосте)

ports:
  - "15672:15672"  # http://localhost:15672 — веб-интерфейс RabbitMQ
  - "5672:5672"   # pika подключается: host="localhost", port=5672
Внутри docker-сети (parser_network) порты открывать не нужно!
Контейнеры в одной сети общаются напрямую по имени сервиса:

parser → rabbitmq:5672 (внутри сети, без проброса портов)
ты → localhost:5672 (снаружи, через проброс портов)

Вот почему в .env пишут RABBITMQ_HOST=rabbitmq — это имя сервиса в compose, оно работает как DNS-имя внутри сети.

💾 Volumes (тома)

Контейнер — ephemeral (временный). Если удалить контейнер MongoDB — все данные исчезнут. Том решает это.

# Именованный том (named volume) — Docker сам управляет
volumes:
  - mongo_data:/data/db
#   ↑           ↑
#   |           └── где MongoDB хранит данные ВНУТРИ контейнера
#   └─────────────── имя тома на хосте (Docker управляет расположением)

# Объявление тома в конце файла:
volumes:
  mongo_data:  # создаёт управляемое хранилище

Named Volume (здесь)

mongo_data:/data/db
Docker сам выбирает где на хосте хранить
Живёт между пересозданиями контейнера
Обычно в /var/lib/docker/volumes/

Bind Mount (альтернатива)

/home/user/data:/data/db
Ты указываешь конкретную папку на хосте
Удобно для разработки (видишь файлы напрямую)

Вывод: удали контейнер mongo, запусти снова — все новости на месте, потому что данные в томе mongo_data, а не в контейнере.

🌐 Networks (сети)

Без явной сети контейнеры не видят друг друга по имени. Сеть создаёт изолированное виртуальное пространство.

networks:
  parser_network:
    driver: bridge
# bridge = стандартная изолированная сеть
# Все контейнеры в ней видят друг друга по имени сервиса
Как работает DNS внутри сети:
Когда парсер подключается к RabbitMQ, он использует хост rabbitmq (имя сервиса).
Docker автоматически резолвит rabbitmq → IP-адрес контейнера.
Это как /etc/hosts, но автоматически.

Итоговая схема сетевого взаимодействия

┌─────────────────────────────────────────────────┐
│  parser_network (Docker bridge network)          │
│                                                   │
│  ┌──────────┐  rabbitmq:5672  ┌───────────────┐  │
│  │ web_app  │ ─────────────→  │   rabbitmq    │  │
│  │ (parser) │                 │ (контейнер)   │  │
│  │          │  mongo:27017    └───────────────┘  │
│  │          │ ─────────────→  ┌───────────────┐  │
│  └──────────┘                 │     mongo     │  │
│                               │ (контейнер)   │  │
└───────────────────────────────└───────────────┘──┘
        ↑                              ↑
        │                    localhost:27017 (снаружи)
   benzinga.com              localhost:5672 (снаружи)
   (интернет)                localhost:15672 (веб UI)

8.5. .env файл — как конфигурация попадает в контейнеры

Вот полный .env этого проекта:

# RabbitMQ
RABBITMQ_HOST="rabbitmq-container"   # имя контейнера из docker-compose
RABBITMQ_PORT="5672"
RABBITMQ_USERNAME="<your_username>"
RABBITMQ_PASSWORD="<your_password>"
RABBITMQ_QUEUE_NAME="news_queue"

# MongoDB
MONGO_USER="<your_username>"
MONGO_PASSWORD="<your_password>"
MONGO_HOST="mongo-container"           # имя контейнера из docker-compose
MONGO_PORT="27017"
MONGO_DB_NAME="<your_db_name>"
MONGO_COLLECTION_NAME="<your_collection>"

DELAY_TIME="5"

Разбор каждой переменной

ПеременнаяЗначениеПочему именно так
RABBITMQ_HOST rabbitmq-container Это container_name из docker-compose. Внутри docker-сети контейнеры находят друг друга по этому имени. Не localhost — парсер и RabbitMQ в разных контейнерах.
RABBITMQ_PORT 5672 Стандартный AMQP порт. Внутри docker-сети пробрасывать не нужно — порт открыт между контейнерами напрямую.
RABBITMQ_QUEUE_NAME news_queue Придуманное нами имя очереди. Должно совпадать у producer (парсер) и consumer (любой читатель очереди).
MONGO_HOST mongo-container Аналогично — container_name MongoDB в docker-compose. Из него строится URI: mongodb://user:user@mongo-container:27017
MONGO_DB_NAME Storage Название базы данных. MongoDB создаст её автоматически при первой записи.
MONGO_COLLECTION_NAME News Название коллекции (≈ таблица в SQL). Тоже создаётся автоматически.
DELAY_TIME 5 Пауза между итерациями парсинга в секундах. В config.py: int(os.getenv('DELAY_TIME')) — конвертируется из строки в число.

Как .env попадает в контейнер — цепочка

# Шаг 1 — docker-compose.yml читает .env и передаёт в контейнер:
env_file:
  - .env   # все KEY=VALUE из файла становятся переменными окружения контейнера

# Шаг 2 — config.py читает переменные окружения:
from dotenv import load_dotenv
load_dotenv()  # нужно если запускаешь БЕЗ docker (локально)

RABBITMQ_HOST = os.getenv('RABBITMQ_HOST')  # → "rabbitmq-container"
MONGO_URI = f"mongodb://{MONGO_USER}:{MONGO_PASSWORD}@{MONGO_HOST}:{MONGO_PORT}"
# → "mongodb://user:user@mongo-container:27017"

# Шаг 3 — app.py использует константы из config:
rabbit = RabbitSender(host=config.RABBITMQ_HOST, ...)  # host="rabbitmq-container"
mongo  = MongoStorage(mongo_uri=config.MONGO_URI, ...)  # uri собран из частей
Зачем нужен load_dotenv() если docker-compose уже передаёт переменные?

Если запускаешь через docker-compose — load_dotenv() не нужен, переменные уже в окружении контейнера.
Если запускаешь локально без Docker (python src/app.py) — нужен, чтобы прочитать .env файл.

Библиотека python-dotenv умная: если переменная уже есть в окружении — не перезаписывает. Поэтому код работает в обоих сценариях.
Безопасность .env должен быть в .gitignore!

Этот репо публичный. Если закоммитить .env с реальными паролями — они попадут в интернет навсегда (даже если потом удалишь коммит, история сохраняется).

В репо кладут .env.example с заглушками: 
RABBITMQ_HOST=your_container_name
RABBITMQ_PASSWORD=your_password
...
А .env с реальными значениями — только локально.

Итог: .env связывает docker-compose ↔ Python код

docker-compose.yml              .env                     config.py
──────────────────             ──────────────────        ──────────────────
container_name:            →   RABBITMQ_HOST=         →  os.getenv(...)
  rabbitmq-container             rabbitmq-container

ports: "5672:5672"         →   RABBITMQ_PORT=5672     →  pika.ConnectionParameters(
                                                            host=RABBITMQ_HOST,
environment:               →   RABBITMQ_USERNAME=***      port=RABBITMQ_PORT,
  RABBITMQ_DEFAULT_USER:         RABBITMQ_PASSWORD=***     credentials=...
    ***                                                   )

9. Архитектура + SOLID — что хорошо и что плохо

Принципы SOLID

Single Responsibility — каждый класс делает одно дело
Parser парсит. RabbitSender отправляет. MongoStorage сохраняет. Они не смешаны.
Open/Closed — открыт для расширения, закрыт для изменения
Чтобы добавить PostgreSQL — создаёшь PostgresStorage, не трогаешь Parser
Liskov Substitution — подкласс заменяем без поломки
MongoStorage и любой другой DatabaseStorage взаимозаменяемы для Parser
Interface Segregation — интерфейс не должен быть жирным
MessageBroker имеет только send(). DatabaseStorage — connect/save/find_news. Минимально необходимое.
Dependency Inversion — зависи от абстракций, не от конкретных классов
Главный принцип здесь!
Parser не импортирует RabbitSender или MongoStorage. Он работает с интерфейсами MessageBroker и DatabaseStorage.

Dependency Injection на примере

# ❌ БЕЗ DI — Parser сам создаёт зависимости (плохо)
class Parser:
    def __init__(self):
        self.broker = RabbitSender(...)   # жёсткая зависимость
        self.storage = MongoStorage(...)  # не заменишь без правки Parser

# ✅ С DI — зависимости передаются снаружи (хорошо)
class Parser:
    def __init__(self, *, message_broker: MessageBroker, database_storage: DatabaseStorage):
        self.message_broker = message_broker    # любой MessageBroker
        self.database_storage = database_storage # любой DatabaseStorage

# В тестах можно передать Mock-объекты вместо реальных
# В продакшне передаётся реальный RabbitSender и MongoStorage

Что сделано хорошо

  • ✓ Интерфейсы (Interfaces.py) — чёткие контракты для брокера и хранилища
  • ✓ Dependency Injection — Parser не знает о MongoDB/RabbitMQ конкретно
  • ✓ async/await — параллельная загрузка статей через asyncio.gather()
  • ✓ Config через env — все настройки в .env, нет хардкода
  • ✓ durable=True + delivery_mode=2 — сообщения не теряются при рестарте
  • ✓ Дедупликация — find_news() проверяет, была ли уже эта статья

Что сделано плохо / можно улучшить

  • ✗ time.sleep() в async коде — блокирует event loop. Нужно await asyncio.sleep()
  • ✗ Соединение с RabbitMQ при каждом сообщении — медленно. Лучше переиспользовать соединение
  • ✗ Новый клиент MongoDB при каждом вызове connect() — лишние ресурсы. Один клиент в __init__
  • ✗ depends_on не ждёт готовности сервиса — только запуска контейнера. Поэтому в app.py есть time.sleep(5) — костыль. Правильно: healthcheck
  • ✗ MessageBroker.send() — синхронный в async коде — интерфейс не согласован с async def run()

Итоговая карта проекта

📁 Parser/
│
├── 🐳 Dockerfile          ← рецепт образа для web_app
├── 🐳 docker-compose.yml  ← оркестрация: web_app + mongo + rabbitmq
├── 📄 requirements.txt    ← зависимости Python
├── 🔐 .env                ← секреты (не в git!)
│
└── 📁 src/
    ├── config.py          ← читает .env, создаёт logger
    ├── Interfaces.py      ← абстрактные классы (контракты)
    ├── parser.py          ← ядро: HTTP → HTML → BeautifulSoup → данные
    ├── rabbit_sender.py   ← реализация MessageBroker через pika
    ├── mongo_storage.py   ← реализация DatabaseStorage через motor
    └── app.py             ← точка входа: собирает всё вместе, запускает цикл
Главный паттерн проекта:

Интерфейсы.py → определяют контракт
rabbit_sender.py / mongo_storage.py → реализуют контракт
app.py → создаёт реализации и передаёт в Parser
parser.py → работает только с контрактами, ничего не знает о RabbitMQ/MongoDB

Это Dependency Inversion + Dependency Injection — самый важный паттерн из SOLID для подобных систем.

10. Проверка понимания — что верно, что нужно уточнить

Разбор твоих слов по пунктам:

✅ Образ — скачали, наполнили, готов

Верно. Процесс такой:

  1. FROM python:3.11-slim — Docker скачивает базовый образ с Docker Hub (один раз, кэшируется)
  2. Каждая инструкция Dockerfile добавляет слой поверх
  3. docker build -t parser_app . — собирается финальный образ и живёт на твоём компьютере
Образ — это неизменяемый снапшот. Его можно запускать сколько угодно раз, он не меняется.

✅ При запуске контейнера всё уже загружено, запускается только программа

Верно. Когда делаешь docker run (или docker-compose up):

  • Docker берёт готовый образ (пакеты уже установлены)
  • Создаёт из него контейнер (изолированный процесс)
  • Запускает CMD ["python", "src/app.py"]
Никакой установки пакетов при старте — всё уже внутри образа. Контейнер стартует быстро.

✅ Образ кэшируется, не надо пересобирать если ничего не менялось

Верно, и это важно понять точнее: Docker кэширует слои. Каждая строка Dockerfile — слой.

FROM python:3.11-slim        ← слой 1 (кэш: скачан один раз)
WORKDIR /app                 ← слой 2 (кэш)
COPY requirements.txt .      ← слой 3 (кэш: пока requirements.txt не изменился)
RUN pip install ...          ← слой 4 (кэш: самый долгий — пакеты)
COPY . .                     ← слой 5 (ПЕРЕСОБИРАЕТСЯ при каждом изменении кода)
CMD [...]                    ← слой 6
Изменил parser.py? Пересобираются только слои 5–6. Слои 1–4 берутся из кэша за секунды.

✅ docker-compose — не нужно руками запускать каждый контейнер

Верно. Без compose пришлось бы:

# Вручную — боль
docker network create parser_network
docker volume create mongo_data
docker run -d --name mongo-container --network parser_network \
  -e MONGO_INITDB_ROOT_USERNAME=user -e MONGO_INITDB_ROOT_PASSWORD=user \
  -p 27017:27017 -v mongo_data:/data/db mongo:7.0.4-jammy
docker run -d --name rabbitmq-container --network parser_network \
  -e RABBITMQ_DEFAULT_USER=user -e RABBITMQ_DEFAULT_PASS=user \
  -p 5672:5672 -p 15672:15672 rabbitmq:management
docker build -t parser_app .
docker run -d --network parser_network --env-file .env parser_app

# С compose — одна команда
docker-compose up -d

✅ Контейнеры общаются через порты и сеть

Верно. Контейнер — изолированный процесс. Два способа связи:

Внутри docker-сети — по имени сервиса, без явного открытия портов:
web_app → rabbitmq:5672 (работает внутри parser_network)

Снаружи — только через проброс портов (ports: в compose):
ты → localhost:5672 (ты на хосте заходишь в RabbitMQ)

⚠️ Про порты на сервере — небольшое уточнение

Ты написал: "подключаюсь к серверу... localhost:portnumber"

Точнее так:

СценарийАдрес
Ты на том же сервере (через SSH)localhost:27017 ✓
Ты со своего компьютера к серверу123.45.67.89:27017 (IP сервера)
Внутри docker-сети (контейнер→контейнер)mongo:27017 (имя сервиса)

Важно: если ты открыл порт 27017 на сервере — он торчит в интернет. MongoDB без пароля + открытый порт = катастрофа. В проекте пароль есть (MONGO_INITDB_ROOT_PASSWORD) — хорошо. В продакшне порты БД обычно не открывают наружу — только приложение внутри docker-сети имеет доступ.

✅ Volumes — данные живут вне контейнера

Верно. Ключевая идея: контейнер — одноразовый. Можно удалить, пересоздать, обновить — не страшно.

# Без volume — данные в контейнере:
docker rm mongo-container → все данные MongoDB исчезли навсегда

# С volume:
volumes:
  - mongo_data:/data/db
# /data/db (внутри контейнера) = mongo_data (том на хосте)
# docker rm mongo-container → данные остались в томе mongo_data
# docker-compose up → новый контейнер подключился к тому → все данные на месте

Путь внутри контейнера /data/db — это стандарт MongoDB, она всегда пишет туда.
Том mongo_data — Docker сам решает где хранить на хосте (обычно /var/lib/docker/volumes/mongo_data/).

Итоговая схема жизненного цикла

СБОРКА (один раз, или при изменении кода):
  Dockerfile → docker build → Image (лежит на диске, неизменяем)

ЗАПУСК (каждый раз):
  Image → docker run / docker-compose up → Container (живой процесс)

ДАННЫЕ:
  Container (ephemeral) ←→ Volume (persistent, на хосте)

СВЯЗЬ МЕЖДУ КОНТЕЙНЕРАМИ:
  Все в одной network → видят друг друга по имени сервиса

СВЯЗЬ СНАРУЖИ:
  ports: "HOST:CONTAINER" → localhost:PORT (локально) или IP:PORT (сервер)
